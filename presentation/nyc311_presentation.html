Step 2

The Journey to the Right Stack

Initial Plan — Azure + ADF

  • Provisioned Azure Data Lake Storage (ADLS Gen2) — storage account with containers for raw / staged data
  • Azure Data Factory to orchestrate copy from the 311 API into the lake

Classic lake-first cloud ingestion pattern.

Where it broke down

  • Pagination. Socrata requires explicit limit/offset over millions of rows
  • Expressing that loop in ADF's copy/lookup/until activities became complicated and brittle
  • Looked at Snowpipe — it ingests files already staged in storage; doesn't call an API and paginate

Decision — dlt + Airflow + Snowflake

  • Pagination = a Python generator loop — natural, testable
  • dlt gives schema inference, typing & merge/upsert for free
  • Airflow gives scheduling, retries, backfill & lineage
  • Warehouse-agnostic (same code targets Snowflake or ClickHouse)
The blocker wasn't Azure — it was forcing a code-shaped problem (paginated API + typed merge) into a drag-and-drop ETL tool.
Step 3

dlt + Airflow + Snowflake

Extraction

  • Airflow passes dlt a bounded created_date window
  • Generator paginates: $limit / $offset / $order / $where
  • Each row: timestamps parsed, coords cast to float, location JSON serialized
  • Retry with backoff on 429 / 5xx

Loading into Snowflake

  • primary_key = "unique_key"
  • write_disposition = "merge" — same key = update, not duplicate
  • Lands in NYC311.NYC_311.SERVICE_REQUESTS_DLT
  • dlt auto-creates & evolves the schema

Step 3 · Orchestration

Two DAGs — and an Event-Driven Hand-off

DAILY nyc_311_dlt_incremental

  • Reloads a 3-day overlap window — catches late status / closure updates via merge
  • @daily · 2 retries · 5-min delay

MANUAL nyc_311_dlt_backfill_monthly

  • One mapped task per month — failures retry at month granularity
  • Used once to load 2020 → now

Dataset-triggered dbt

Both dlt DAGs produce an Airflow Dataset on success. The dbt Cloud DAG is scheduled on that URI — successful load automatically triggers dbt, no cron coupling.

Step 4 · Detail

dbt — Layers, Macro, Seeds & Tests

Gold — why incremental?

fct_service_requests has tens of millions of rows. Filtering on ingested_at > max(ingested_at) and merging on service_request_id touches only new or mutated rows each run.

Gold — why marts are tables?

Marts are small aggregates (counts & rates). Full rebuild each run is cheap and keeps them consistent — incremental logic would add complexity with no benefit.

Macro — clean_sentinel

NYC 311 uses placeholders for "no value" that aren't NULL:

''  Unspecified  N/A  0 Unspecified  Unknown

One macro trims whitespace and collapses all of them to NULL — called on many columns in silver. Write once, apply everywhere.

Seeds — version-controlled reference lists

  • seed_agency_codes — flag unexpected agencies
  • seed_location_types — flag unexpected location types
  • seed_expected_source_columns — schema-drift contract

Tests

  • unique + not_null on all keys
  • accepted_values — borough & channel (error); status & facility (warn)
  • relationships → seeds for agency & location type
  • regex / range — ZIP, BBL, lat/long bounding box
  • expression_is_true — closed ≥ created, created not in future
  • Schema-drift guard — compares live warehouse columns vs. seed manifest; flags MISSING and NEW columns

Failing rows persist to *_DQ_FAILURES schema for triage.

Step 6 · Known limitation

Limitation & Summary

The overlap window gap
Data is loaded filtered by created_date with a 3-day overlap. Requests updated within those 3 days are re-merged correctly — but requests created earlier whose status later changes are missed.

Why it happens

Windowing on created_date is efficient, but a 311 request can be updated long after creation (e.g. opened in January, closed in June). Those late mutations fall outside the window.

Possible mitigations

  • Add a second pass on resolution_action_updated_date
  • Widen the overlap window (cost vs. freshness trade-off)
  • Periodic reconciliation backfill of open requests
