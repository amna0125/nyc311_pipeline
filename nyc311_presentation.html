What is a "311" request?

Every non-emergency complaint or service request New Yorkers file — noise, potholes, heating, sanitation, illegal parking — tagged with the responding agency, complaint type, borough, status, timestamps and geolocation.

Why it's a good engineering subject

  • Large & growing — needs real incremental loading, not full reloads.
  • Messy — sentinel "missing" values, bad ZIPs, out-of-range coordinates.
  • Mutable — a request's status/closed date changes after creation.
The endpoint https://data.cityofnewyork.us/resource/erm2-nwe9.json supports SoQL filtering ($where, $limit, $offset, $order) — the foundation for our paged, windowed extraction.

2Initial Plan — Azure + ADF

The first design targeted a fully Azure-native stack.

What we set up

  • Azure Data Lake Storage (ADLS Gen2) as the landing zone — provisioned the storage account and containers for raw / staged data.
  • Azure Data Factory (ADF) to orchestrate the copy from the 311 API into the lake.

A classic "lake-first" cloud ingestion pattern.

Where it broke down

  • API limitations. The Socrata endpoint requires explicit pagination (limit/offset over millions of rows).
  • Expressing that paging loop in ADF's copy/lookup/until activities became complicated and brittle — a lot of pipeline plumbing for a simple "page through an API" job.
  • Hard to make incremental, retry-safe, and readable.
The blocker wasn't Azure itself — it was forcing a code-shaped problem (API pagination + typing + merge) into a drag-and-drop ETL tool.

2Evaluating Alternatives → The Pivot

Considered: Snowpipe

Snowflake's auto-ingest service. But Snowpipe ingests files already staged in cloud storage — it loads from a stage, it doesn't call an API and paginate.

It solves loading, not extraction — we'd still need something to pull & page the API first.

Chosen: dlt + Airflow + Snowflake

  • dlt → handles extraction + typed loading + merge/upsert.
  • Airflow → schedules & controls the time windows.
  • Snowflake → the analytics warehouse.

Why this won

  • Pagination is just a Python generator loop — natural, testable.
  • dlt gives schema inference, typing & merge for free.
  • Airflow gives scheduling, retries, backfill & lineage.
  • Warehouse-agnostic (same code targets Snowflake or ClickHouse).

3dlt + Airflow + Snowflake

Airflow owns orchestration; dlt owns destination-specific loading.

Extraction (the dlt source)

  • Airflow passes dlt a bounded created_date window.
  • Pagination lives in a generator: $limit / $offset / $order / $where — a 200k-row month becomes 4 calls at 50k/page.
  • Each row is normalized: timestamps parsed, coordinates cast to float, the location object serialized to JSON.
  • Retry with backoff on 429/5xx; raw & staged JSON snapshots written to disk for replay.

Loading (the dlt resource)

  • primary_key="unique_key"
  • write_disposition="merge" — reloading the same key updates / deduplicates instead of appending.
  • dlt auto-creates & evolves the schema in Snowflake.
  • Lands in NYC311.NYC_311.SERVICE_REQUESTS_DLT.
@dlt.resource(name=table_name,
              primary_key="unique_key",
              write_disposition="merge")   # merge = upsert on unique_key
def service_requests():
    yield from service_request_rows(window)   # paged + normalized rows

3Two Airflow DAGs

DAILY  nyc_311_dlt_incremental

  • Runs @daily, catchup=False, max_active_runs=1.
  • Reloads a small recent overlap window (default 3 days) so late status/closure updates are captured by the merge.
  • 2 automatic retries with a 5-min delay.

MANUAL  nyc_311_dlt_backfill_monthly

  • One mapped task per month across a date range.
  • max_active_tasks=1 — months load sequentially so failures retry at month granularity.
  • Used once to load history back to 2020.

Data-aware scheduling — the hand-off to dbt

Both DAGs "produce" an Airflow Dataset on success:

Dataset("snowflake://NYC311/NYC_311/SERVICE_REQUESTS_DLT")

The dbt DAG is scheduled on that exact dataset URI, so a successful load automatically triggers transformation — no fragile cron coupling, no polling.

4dbt — Transformation Layer

A standalone dbt project (../nyc311-dbt) running in dbt Cloud, following the Medallion architecture.

Two environments (isolation by target schema)

DevDBT_AMNAsame raw

Both read the same raw SERVICE_REQUESTS_DLT; the +schema: configs append _BRONZE/_SILVER/_GOLD so dev & prod never collide.

Production job orchestration

  • The Prod job runs dbt deps → dbt seed → dbt build.
  • Airflow triggers it via the dbt Cloud API (DbtCloudRunJobOperator) — fired by the dataset the dlt load produces.
  • Airflow waits for termination, so the task reflects the real dbt run status.

Net effect: incremental load completes → dbt build runs → tests run, end to end, automatically.

Bronze  Layer — Faithful Mirror

Materialized as views. A 1:1, typed mirror of the dlt landing table.

stg_nyc311__service_requests.sql

  • Rename to clean, consistent names; cast types (datetimes → timestamp_ntz, coords → float, location → VARIANT).
  • Explicit column selection (no select *) — if the API drops/renames a column, the model fails loudly instead of losing data silently.
  • Defensive dedup via row_number() on unique_key — keeps the latest row even if a merge load left duplicates.

Why two .yml files?

_bronze__sources.yml — describes the raw warehouse data: declares the source, checks freshness (warn 36h / error 72h), and tests unique + not_null on the key.

_bronze__models.yml — describes the models we build in dbt.

Keeping "raw inputs" and "our models" in separate files makes each one easier to scan and reason about.

Silver  Layer — Clean & Enrich

Materialized as views. Two steps: standardize, then derive.

Step 1 · Cleaned

int_service_requests__cleaned.sql

  • Replaces junk / sentinel values ('', Unspecified, N/A, Unknown) with NULL.
  • Standardizes controlled vocabularies to canonical UPPER (e.g. borough → MANHATTAN, with park-borough fallback).
  • Enforces structure: drops invalid ZIPs (non 5-digit) and out-of-box coordinates (NYC bounding box).
Step 2 · Enriched

int_service_requests__enriched.sql

  • Adds derived columns: resolution_time_hours, is_closed, is_overdue, is_resolved_on_time.
  • Flattens date parts from created_at (year, quarter, month, day-of-week, weekend flag, hour).
  • Guards against bad data — negative durations (closed before created) → NULL.
Output = the conformed, analytics-ready grain (one clean row per request) that all of gold is built from.

Gold  Layer — Analytics Models

Dimension

table

dim_date — a gap-free calendar spine (weekend/month/quarter attributes) for time-intelligence and zero-activity days. Joined to the fact via created_date_sk.

Fact

incremental · merge

fct_service_requests — wide, one row per request. Descriptive attributes are degenerate dimensions on the fact itself (no needless star joins).

Marts

table (full rebuild)

Aggregated, BI-facing tables: daily volume by borough/agency, SLA/resolution performance, open-vs-closed backlog.

Why the fact is incremental

It's the largest table (tens of millions of rows). Rebuilding it daily is wasteful. Filtering on ingested_at > max(ingested_at) and merging on service_request_id means each run touches only new or mutated rows (status flips, late closures from the overlap reload) and updates them in place.

Why marts are not incremental

Marts are small aggregates (grouped counts & rates) that read from the fact. They're cheap to rebuild fully every run, which keeps them always-consistent and avoids the complexity of incremental merge logic where it buys nothing.

4Macro — clean_sentinel

One macro, reused across many silver columns — DRY data cleaning.

The problem

NYC 311 uses several placeholders that mean "no value" but are not NULL:

'' Unspecified N/A 0 Unspecified Unknown

If left as-is, every downstream model and test has to special-case them.

The solution

A macro that expands into a chunk of SQL: it trims whitespace and collapses all placeholders to NULL, so everything downstream treats "missing" consistently.

Called on many columns in the cleaned model — write the logic once, apply it everywhere.

{% macro clean_sentinel(column) %}
    nullif(nullif(nullif(nullif(nullif(
        trim({{ column }}), ''),
        'Unspecified'), 'N/A'), '0 Unspecified'), 'Unknown')
{% endmacro %}

-- usage in silver:
upper({{ clean_sentinel('borough') }})  as borough

4Seeds — Version-Controlled Reference Lists

Plain CSV files dbt loads into Snowflake as small tables (dbt seed).

seed_agency_codes.csv

Allowed NYC agency acronyms. Used by a warn-severity relationships test to flag unexpected agencies.

seed_location_types.csv

Allowed location-type values. Same idea — surfaces values outside the known set without blocking the build.

seed_expected_source_columns.csv

The list of columns the raw table should have — the contract used to detect if the API changes its schema.

Why seeds? Reference lists that rarely change live better as version-controlled CSVs (reviewable in Git, reusable across tests) than as values hard-coded inside SQL.

4Data Quality — Tests

Layered tests run as part of dbt build; failing rows persist to a *_DQ_FAILURES schema for triage.

Generic & integrity tests integrity

  • unique + not_null on keys (source & every grain).
  • accepted_values — borough & channel (error); status & facility (warn, evolving sets).
  • relationships → seeds for agency & location type.
  • regex / range (dbt_expectations) — ZIP, BBL, lat/long bounding box.
  • expression_is_true — business rules: closed ≥ created, created not in future, due ≥ created.

Schema-drift guard drift

assert_source_schema_unchanged.sql compares the live warehouse columns against seed_expected_source_columns and flags:

  • MISSING/RENAMED — an expected column disappeared upstream.
  • NEW/UNMAPPED — the API added a field we haven't mapped yet.

Severity warn, so a schema change surfaces without halting production loads.

Severity is deliberate: structural / closed-set violations error (block bad data); evolving or known-artifact issues warn (surface, don't block).

Why this layering works

Power BI never touches raw data or transformation logic — it consumes clean, tested, aggregated gold tables. All business logic stays in dbt (versioned, tested), keeping the BI layer thin and the metrics consistent.

6Known Limitation — The Overlap Window

The daily incremental load filters the source by created_date with a 3-day overlap window. Requests updated within those 3 days are re-merged correctly — but requests created earlier whose status later changes are missed.

Why it happens

We page the API on created_date (an immutable field, ideal for windowing). But a 311 request can be updated long after it's created — e.g. a complaint opened in January and closed in June.

The 3-day overlap only re-pulls recently created rows, so a status change on an old request falls outside the window and isn't re-merged.

Possible mitigations

  • Window (or add a second pass) on resolution_action_updated_date to catch mutations regardless of creation date.
  • Widen the overlap window (trades freshness lag for cost).
  • Periodic reconciliation backfill of open/recent requests.

A deliberate trade-off today: cheap, fast daily loads vs. perfect late-update capture.
